# 11 — API Reference

Base URL: `https://<server>/api`. All responses are JSON. Authentication uses the `__Host-ets_sid` session cookie
(`HttpOnly`, `Secure`, `SameSite=Strict`; HTTPS only), which is set by `/auth/login`. Only a lab system with
`COOKIE_SECURE=false` uses the plain name `ets_sid`.

**Idle timeout (1.12.2):** a session ends `SESSION_IDLE_MINUTES` (60) after the last request that carries
**`X-ETS-Activity: 1`** (genuine user activity), or `SESSION_TTL_HOURS` (12) after sign-in, whichever comes first.
Requests without that header — and any request with `X-ETS-Live: 1`, `GET /events`, `POST /presence` — never extend
it. The web app sends the header only from real input (`POST /auth/activity`); the phone app on the requests a person
starts. An ended session answers `401 not_authenticated` (and `/auth/me` `{authenticated: false}`) on every request
from then on, and its cookie is cleared.

**Every POST/PUT/PATCH/DELETE must send** `X-Requested-With: ets` and `Content-Type: application/json`.
A body in another format is refused with `415 unsupported_media_type`. Bodies are limited to 100 kB and 32 levels of
nesting (`413 payload_too_large`, `400 invalid_json`); the file uploads `POST /imports`, `POST /imports/preview`,
`POST /tracker/import` and `PUT /branding/:key` accept up to 5 MB, and `POST /users/import[/preview]` up to 1 MB
(read only after the administrator check). Numeric ids in paths must be whole numbers in
the int4 range (`400 invalid_id`). Bidirectional control characters are removed from text values.

Errors: HTTP status + `{"error": "<code>", ...}`. Codes include `invalid_credentials` (401 — wrong or unknown
username or e-mail address, wrong password, disabled **or paused** account, an address shared by several accounts:
the answer is the same), `too_many_attempts` (429, with
`retry_after` seconds: per-IP / per-account limit on password and 2FA checks, or a paused account at the 2FA step
or a re-authentication), `too_many_requests` (429, general `/api` limit, with `retry_after`), `invalid_code`,
`mfa_required`, `mfa_not_pending`, `not_authenticated`, `forbidden` (with `permission`), `out_of_scope`,
`admin_only`, `csrf_rejected`, `password_change_required`, `weak_password` (with `reasons`), `invalid_value`
(with `field`), `invalid_id`, `invalid_date`, `invalid_json`, `invalid_request`, `payload_too_large`,
`unsupported_media_type`, `requester_not_allowed`, `cannot_approve`, `not_found`, `server_error`,
`pass_requires_100`, `progress_below_100_while_passed`, `import_has_row_errors` (1.8.1, see below), `mandatory_type`,
`invalid_token` (401, `/m/*`), `too_many_devices` (409) (1.9.0), `rename_reason_required`, `rename_must_be_separate`,
`name_unchanged` (400), `name_changed` (409) (1.9.1, see the rename below), `cannot_end_own_session` (400),
`session_not_found` (404) (1.11.0). There is no
`423` / `account_locked` answer.

**«نجح» = 100 % (1.8.1; auto-filled since 1.12.21).** A passed item (`test_status: 2`, plain pass) is always at
progress 100. Setting `test_status` to 2 now **brings the progress up to 100 in the same write** — the server is the
single source of truth: `withPassProgress(cur, changes)` (`services/passRule.js`) adds `progress: 100` to the change
whenever it sets «نجح» below 100, on the single edit (`PATCH /functions/:id`), the bulk set and the edit request it
builds for approval. The bump is added after the per-field permission check, so a user with only `tst` (test-status
permission, not `pct`) can mark «نجح» — the progress coercion rides on the status change. So `test_status: 2` alone,
or with `progress: 100`, or even with a `progress` below 100 (then «نجح» wins and the progress is coerced to 100), is
always accepted; `pass_requires_100` is no longer returned for a direct/bulk «نجح». The clients confirm the auto-fill
first (a dialog for a single item, a confirmation step in the bulk modal). «نجح مع ملاحظة» (`test_status: 1`) has no
progress rule. The progress of a passed item still **cannot be lowered** below 100 while it stays «نجح»
(`progress_below_100_while_passed`) — move the status away from «نجح» first. An item already passed below 100 % before
1.8.1 is left as it is (a bulk «نجح» does not touch its progress), keeps every other edit, and is fixed by either
field. Report items (`item_type: "report"`) follow the same behavior. **Imports keep the 1.8.1 rule** (a row setting
«نجح» below 100 is still a row error — they are not auto-filled). Errors:

| Code | Status | When | Extra fields |
|---|---|---|---|
| `progress_below_100_while_passed` | 400 | The change (single edit or bulk) lowers a progress below 100 on an item that stays «نجح» — unless the same request moves `test_status` away from 2 | single edit: `progress`, `test_status`, `code`; bulk: `bulk`, `count`, `items`, `list` |
| `progress_below_100_while_passed` / `pass_requires_100` | 409 | On approval of an edit request (`/approvals/:id/approve`), or when the saved row of a direct edit would break the rule because of another change at the same moment (rolled back). `pass_requires_100` here means a «نجح» request whose item's progress was lowered by someone else since the request (the approval leaves it «نجح» below 100) | `function_id`, `code`, `progress`, `test_status` |
| `import_has_row_errors` | 400 | `POST /imports` (the chosen part of the file) or `POST /tracker/import`: rows of the file would set «نجح» below 100 % or lower a passed item below 100 %. Nothing is written | `count`, `errors: [{app_id, function_id, code, name_ar, name_en, item_type, error, progress, test_status}]` (up to 200), `list` (`"per/D3, per/D7, … (+n)"`) |

Bulk `items`: `[{function_id, app_id, code, name_ar, name_en, item_type, progress, current_progress, test_status, error}]`
(up to 200) — every counted item that blocks the bulk set; nothing is changed (all or nothing).

Rate limits: password / 2FA / recovery-code checks (`/auth/login`, `/auth/2fa/*`, `/auth/change-password`)
`LOGIN_RATE_LIMIT` (30) per IP per 15 min and 30 failures per typed sign-in name (username or e-mail, trimmed, lower case) per 15 min; every `/api` request
`API_RATE_LIMIT` (600) per IP per minute; nginx adds 10 / min per IP on the sign-in endpoints.

## Release & deploy — `/release` (**Phase 3**, feature-complete, 1.12.20; permission `cfg` **and** role `admin`, 403 otherwise)
Records a **signed promotion intent** only. The API never deploys: it runs unprivileged and holds no push credential; the root agents (`ets-release-publisher` / `ets-deploy-agent`) sign, push, back up, deploy, health-gate, roll back and report back (their live setup is operator-verified — [13 §8a](13-Release-Promotion-Design.md)). Signing key / allow-list come from `ETS_RELEASE_SIGN_KEY`, `ETS_RELEASE_SIGNERS_DIR` (never in the DB or repo). The `GET` endpoints are **read-only** and are the same ones a **production** admin uses to see the deployed state (on prod they read that server's `release_agent_status`); no separate prod endpoint exists.

| Method | Path | Description |
|---|---|---|
| GET | `/release/versions` | `{phase: 3, production: {version, commit, deployed_at, stale}, test: {version, resolved}, signing_ready, versions: [{version, date, title, summary (what-changed from CHANGELOG), commit, commit_source tag\|release_commit, promotable}]}`. Released versions are resolved to a commit by **an annotated tag `v<x.y.z>` when present, else the `release <x.y.z>` commit**; only resolvable versions are listed, `promotable` = newer than production |
| GET | `/release/status` | `{phase: 3, production: {version, commit, deployed_at, stale}, agent: {seen_at, ok (seen < 3 min), apply_error}, current: <promotion>, in_flight, signing_ready}`. Read-only; the deployed version/commit, last deploy time and the **agent heartbeat/staleness** come from `release_agent_status` (written by the prod deploy agent). `current` is the newest promotion row |
| GET | `/release/history` | `{promotions: [<promotion>]}` — newest first, 50 max (the operator audit view). A `<promotion>` carries `{id, version, commit, prev_version, prev_commit, intent, auto_rollback, status requested\|publishing\|deploying\|succeeded\|failed\|rolled_back\|cancelled, signer (key id), backup_ref, requested_by, by_name, authorized_at, finished_at, manifest, progress {phase, prod}, result {health_summary, health_checks, migrated, rollback_action none\|code_rollback\|stop\|stop_needs_db_restore, needs_db_restore, restore_command, log_tail…}, error, …}`. The UI renders each row expandable with the phase progression, the health-check detail and — when `needs_db_restore` — the «استرجاع قاعدة البيانات» panel |
| POST | `/release/promote` | `{version, confirm: <version>, auto_rollback?: bool (default true), password, code? \| recovery_code?}`. Admin + **re-auth (password + OTP)** + confirm (type the version). Resolves the commit, computes `prev_*` from the recorded production version, Ed25519-**signs** the manifest, writes a `release_promotions` row with status `requested`, and raises the **S-REL (S12) `started`** alert to admins → 202 `{promotion, note}`. 400 `invalid_version` / `unknown_version` / `confirmation_phrase_mismatch` / `wrong_password` / `mfa_code_required` / `invalid_code`; 409 `not_newer` / `promotion_in_flight` (one in flight); 503 `release_signing_unavailable`; 10 per hour per administrator (`ETS_RELEASE_PROMOTE_LIMIT`). Audited `release_promote` |
| POST | `/release/rollback` | as `/promote` with `intent: rollback` — records a signed rollback intent to the previous (older, `prev`-matching) version, driving a **code-rollback** promotion. 409 `nothing_to_roll_back` / `rollback_not_older`. Audited `release_rollback` |

The terminal **S-REL (S12)** alerts (`succeeded` / `failed` / `rolled_back`) are raised by the test-side publisher when it pulls the signed production status; `failed` / `rolled_back` are **critical** (phone), and a `failed`-with-migration carries the `ets-restore <backup_ref>` command.
